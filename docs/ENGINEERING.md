## 我怎样使用 AI 推进项目

我从自己的使用需求出发确定产品目标，使用 Codex 参与需求拆解、方案讨论、实现、测试和发布准备。实际使用时，我提供界面反馈、失败现象与验收要求，再推动 AI 对相关代码和证据进行检查。

大量代码和技术分析由 AI 参与完成。个人贡献主要体现在需求判断、任务推进、运行反馈与交付验收；不能把项目采用的每一项技术都等同于本人独立实现或精通。

这项经历包含 Windows 桌面产品、Web 页面、IPC、服务接口、外部数据接入、持久化与发布。AI 是开发工具；TAIL 的界面助手不因此成为已实现的 RAG 或模型交易决策系统。

## 案例 一次持久化快照容量故障

### 运行现象与复现

来源会话的重复观察记录持续累积，快照接近单文件容量上限。在保存的运行副本上追加下一轮恢复观察，能够复现 `Persistent snapshot exceeds configured byte limit`。仅在 UI 展示一个通用运行失败码，无法说明这个原因。

### 处理方式

在既有持久化提交前压缩重复 notification history，保留各来源路径的最早完整 receipt、最新完整 envelope，以及解析或拒绝证据仍引用的记录。恢复事件和缓冲的实时事件在同一次串行 mutation 中提交，随后进行路由去重；并将底层容量原因映射为明确错误码。

对应私有实现提交：`6b51173`。本次公开更新没有改动该实现。

### 隔离测量结果

| 指标 | 原副本 | 压缩后的纯快照 |
| --- | --- | --- |
| 文件长度 | 66,081,733 bytes | 31,237,659 bytes |
| notification observations | 43,937 | 15,017 |
| records | 7,514 | 7,514 |

非 observation 内容的摘要保持不变。实际恢复入口的首次正常提交记录为 1 次写入、31,238,995 bytes，到首次只读 fetch 约 3.2 秒。重启使用同一证据时，目标 observations 保持 2→2，没有重复增加该组观察。

**3.2 秒测量的是本机隔离副本的恢复处理，不是来源买入到跟随买入的延迟。** 不能将它写成三秒实盘成交。该项修复也不证明其他网络、排序或持续运行问题已经解决。

### 这项经历说明什么

可复现的输入、明确的写入行为和数据不变量，能够帮助判断修改究竟处理了哪一个问题。实际运行仍需区分容量、网络、顺序与生命周期故障，不能用测试总数替代当前目标的验收。
